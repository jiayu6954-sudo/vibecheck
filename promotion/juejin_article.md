《我用 Cursor 写代码踩了 3 个坑，于是做了个检查工具》

**副标题：** 不是什么"革命性产品"，就是个辅助检查的小工具

---

## 正文

### 一、真实故事：AI 写的代码"看起来能用"

上周接了个小项目，用 Cursor 写了个 Node.js 后端接口。

开发过程很爽，AI 补全快，测试也通过了，感觉 30 分钟搞定了平时 2 小时的活。

然后部署到线上...

#### 坑 1：API Key 硬编码

```javascript
// Cursor 生成的代码
const openai = new OpenAI({
  apiKey: "sk-abc123def456..." // 直接写死了
});
```

结果：
- 推送到 GitHub 后，5 分钟收到 Secret Scanning 警告邮件
- 赶紧 revoke key，重新申请
- 改成环境变量

**为什么 AI 会这样写？**
因为示例代码通常是这样的，AI 学习了这个"坏习惯"。

---

#### 坑 2：SQL 注入风险

```javascript
// Cursor 生成的代码
app.get('/user/:id', async (req, res) => {
  const userId = req.params.id;
  const result = await db.query(
    `SELECT * FROM users WHERE id=${userId}` // 直接拼接！
  );
  res.json(result);
});
```

测试时没问题，因为我传的都是正常 ID。

但如果有人传 `1 OR 1=1--`，整个用户表就泄露了。

**为什么 AI 会这样写？**
因为直接拼接"看起来更简洁"，而且在演示代码中很常见。

---

#### 坑 3：未处理的异步错误

```javascript
// Cursor 生成的代码
app.post('/upload', async (req, res) => {
  const file = await processFile(req.file); // 如果这里报错呢？
  res.json({ success: true, file });
});
```

开发环境没事，线上偶尔报 `UnhandledPromiseRejectionWarning`。

因为 `processFile` 可能会因为文件格式问题抛出异常，但没有 `try-catch`。

**为什么 AI 会这样写？**
因为 "happy path"（正常流程）的代码更简洁，异常处理会增加复杂度。

---

### 二、为什么不直接问 Claude？

发现这些问题后，我想"以后用 AI 写代码，先让 Claude 检查一遍"。

试了几次，发现几个问题：

#### 问题 1：提示词不好写

第一次问：
> "帮我检查这段代码"

Claude 回答：
> "代码看起来不错，结构清晰..."（完全没检查出问题）

第二次问：
> "帮我检查这段代码的安全问题，特别是 SQL 注入、XSS、敏感信息泄露"

这次检查出来了，但每次都要写这么长的提示词，太累。

---

#### 问题 2：输出格式不统一

有时候 Claude 会：
- 长篇大论（200 字解释一个小问题）
- 太简略（只说"有风险"，不说怎么改）
- 顺序混乱（先说小问题，后说致命问题）

想要一个统一的格式：
```
评分：75/100
Critical：1 个
High：2 个
Medium：3 个

[具体问题] + [位置] + [修复建议]
```

---

#### 问题 3：Claude 不会检查"自己的习惯"

比如：
- AI 喜欢创建很多抽象类（过度工程）
- AI 喜欢到处 try-catch（防御式编程过度）
- AI 生成的注释太多（代码 10 行，注释 20 行）

直接问 Claude，它不太会主动指出这些，因为这是它自己的"风格"。

---

#### 问题 4：贵

Claude API：¥0.26/次（输入 2000 tokens + 输出 1000 tokens）

每天检查 10 次代码 = ¥2.6
一个月 = ¥78

对个人开发者来说，有点心疼。

### 四、技术实现（简单说）

#### 架构

```
前端（Next.js） → 后端 API → DeepSeek API
                    ↓
                保存历史（Supabase）
```

#### 核心提示词

```javascript
const SYSTEM_PROMPT = `
你是代码安全分析专家，专门检测 AI 生成代码的问题。

重点检查：
1. 硬编码密钥、密码
2. SQL 注入、XSS
3. 未处理的异步错误
4. 过度工程、不必要的抽象
5. ...

输出格式：严格 JSON
{
  "score": 0-100,
  "issues": [
    {
      "severity": "critical|high|medium|low",
      "title": "...",
      "location": "...",
      "fix": { "description": "...", "code": "..." }
    }
  ]
}
`;
```

这个提示词是反复调试出来的，比随手问 Claude 效果好。

---

#### 为什么用 DeepSeek？

1. **便宜**：¥0.005/次 vs Claude 的 ¥0.26/次
2. **国内快**：访问速度稳定
3. **质量够用**：检测这些常见问题，DeepSeek 够了

当然，Claude 更好，但对这个场景来说，性价比不高。

### 五、发现的典型问题（真实数据）

上线 3 天，收到 50 多次扫描，统计了一下问题分布：

| 问题类型 | 出现次数 | 占比 |
|---------|---------|------|
| 硬编码敏感信息 | 12 | 24% |
| SQL 注入风险 | 8 | 16% |
| 未处理异步错误 | 15 | 30% |
| 过度工程 | 6 | 12% |
| 其他 | 9 | 18% |

**结论：** 未处理异步错误是最常见的问题。

---

#### 案例 1：硬编码 API Key（Critical）

**问题代码：**
```javascript
const client = new Client({
  apiKey: "sk-abc123",
  apiSecret: "secret-xyz"
});
```

**修复建议：**
```javascript
const client = new Client({
  apiKey: process.env.API_KEY,
  apiSecret: process.env.API_SECRET
});
```

**为什么重要？**
一旦推送到 GitHub，密钥立即泄露，可能被滥用。

---

#### 案例 2：SQL 注入（High）

**问题代码：**
```javascript
const users = await db.query(
  `SELECT * FROM users WHERE email='${email}'`
);
```

**修复建议：**
```javascript
const users = await db.query(
  'SELECT * FROM users WHERE email=?',
  [email]
);
```

**为什么重要？**
攻击者可以构造 `email=' OR '1'='1`，绕过验证。

---

#### 案例 3：未处理 Promise（Medium）

**问题代码：**
```javascript
app.get('/data', async (req, res) => {
  const data = await fetchData();
  res.json(data);
});
```

**修复建议：**
```javascript
app.get('/data', async (req, res) => {
  try {
    const data = await fetchData();
    res.json(data);
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
});
```

**为什么重要？**
如果 `fetchData()` 失败，整个进程可能崩溃。

### 六、局限性（重要）

这不是什么"AI 代码审查专家"，有很多局限：

#### 1. 不能替代人工审查

复杂的业务逻辑、并发问题、性能优化，还是要人看。

这个工具只能检查"显而易见的问题"。

---

#### 2. 可能有误报

底层是 AI（DeepSeek），会有误判。

建议：
- **Critical/High 问题**：一定要检查
- **Medium/Low 问题**：参考就好

---

#### 3. 目前功能简单

- 没有 IDE 插件（要手动复制粘贴）
- 没有 CI/CD 集成
- 没有自定义规则

这些都在规划中，但现在就是个 MVP。

#### 用户反馈 2："误报了一个问题"

> 用户提交了一个案例：工具报"SQL 注入"，但实际是内部管理接口，没有公开。

#### 用户反馈 3："能检测 Python 代码吗？"

**回应：**
可以做，需要：
1. 研究 Python 常见的 AI 代码问题
2. 针对性优化提示词

### 八、数据 & 开源

#### 隐私保护

很多人关心代码会不会泄露：

**现状：**
- 代码只用于一次性扫描，不存储
- DeepSeek API 不保存用户数据（官方承诺）
- 服务器日志只记录扫描次数，不记录代码

**未来：**
- 开源核心代码（让大家看到怎么处理的）
- 提供本地部署版本（企业用户）

---

#### 开源计划

**为什么现在不开源？**

想先把核心功能做稳定，避免：
- 开源后一堆 issue（我一个人处理不过来）
- 代码质量不高被吐槽
- 没有文档，别人看不懂

**什么时候开源？**

当满足以下条件：
1. 核心功能稳定（误报率 <10%）
2. 有完整文档
3. 有 100 个真实用户验证

预计：1-2 个月后。

### 九、总结

#### 这个工具适合谁？

✅ **适合：**
- 用 Cursor/Copilot/Claude Code 写代码的人
- 想快速检查常见问题的人

- 已经有完善代码审查流程的公司
